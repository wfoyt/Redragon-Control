# Redragon Control 0.2.6

**Redragon Control is moving from Flatpak releases to AppImage.** New releases
will ship as AppImages; the Flatpak distribution is retired. This release
includes all changes since the last published release, **0.2.2**, including the
0.2.3–0.2.5 development work.

## Download and migration

Download `Redragon-Control-0.2.6-x86_64.AppImage`, make it executable, and run it:

```bash
chmod +x Redragon-Control-0.2.6-x86_64.AppImage
./Redragon-Control-0.2.6-x86_64.AppImage
```

Flatpak users: export your profiles from the old app first, quit its keyboard
services, then import the profiles into the AppImage. AppImage settings live in
`~/.config/redragon-control`; previous Flatpak settings remain under
`~/.var/app/io.github.redragon.Control/`. Existing host device permissions remain
usable. Users do not need Flatpak to run the AppImage.

## Complete changelog since 0.2.2

### AppImage distribution and hardware setup

- Bundle Python, GTK 3/4, libadwaita, evdev, AppIndicator libraries, fonts, licenses,
  and a GNOME 50 userspace with its dynamic loader in an x86_64 AppImage.
- Use Cairo rendering to reduce reliance on host GPU drivers. Support
  `--appimage-extract-and-run` where FUSE is unavailable.
- Add **Enable keyboard access** on the first setup page. The bundled helper
  authenticates through Polkit, installs device-specific udev rules, and enables
  uinput. The app and its services stay unprivileged.
- Report cancelled authentication, missing authorization support, timeouts, and
  setup failures; prompt for reconnection when permissions need refreshing.
- Stage the helper in a private host directory and use a minimal host environment
  so administrator setup does not depend on a user-mounted image or bundled libraries.
- Route normal and explicit real `gui` launches through the tray to keep the
  AppImage mount available to remapping and Settings. Preserve direct demo/CLI behavior.
- Use the bundled Python launcher for child processes. Recognize and stop daemons
  across separate AppImage mounts by validating their command, executable, user,
  and settings path.
- Remove the installable Flatpak manifest, entry point, portal startup gate, and
  obsolete tests. Build dependencies independently of an application Flatpak;
  recreate the AppDir on each build to prevent retired files leaking into releases.

### Login startup and Gear Lever updates

- Enable login startup on first normal launch, using XDG autostart for GNOME and
  KDE Plasma and a post-boot hook on Omarchy without editing Hyprland configuration.
- Add **Launch at login** to the tray and `autostart enable`, `disable`, and
  `status` CLI controls. Preserve desktop opt-outs and deleted startup entries.
- Register the AppImage's permanent path instead of its temporary mount; refresh
  that path when a moved image is launched. Handle paths containing spaces and
  reserved characters. Demo and custom-settings launches do not auto-register.
- Resume enabled remapping after login and reconnects; quitting stops services
  for the session while retaining the next-login preference. Saved onboard
  lighting needs no background process.
- Embed the GitHub stable-release update source recognized by Gear Lever and
  generate matching `.AppImage.zsync` and `.AppImage.sha256` release files.
- Require matching update assets in the build and document the release checklist
  in `AGENTS.md` so future releases preserve update support.

Gear Lever discovers the embedded source without manually entering a URL.
Users still control checking for and installing updates in Gear Lever; this is
not a promise of silent unattended installation. Enable background checking in
Gear Lever if desired. Older AppImages without metadata need one manual upgrade
or a one-time GitHub source configuration: repository `wfoyt/Redragon-Control`,
filename `Redragon-Control-*-x86_64.AppImage`, prereleases disabled.

### Desktop appearance

- Add Automatic, Adwaita, and Omarchy choices under **Menu → Appearance** and
  `theme auto`, `theme adwaita`, and `theme omarchy` CLI commands.
- Detect Omarchy automatically; use Adwaita elsewhere. Follow the current Omarchy
  palette live, including theme-file replacement and older theme layouts.
- Validate palettes, provide fallback colors, and respect high-contrast settings.
- Store appearance separately in `config.appearance.json` so keyboard profiles
  cannot override it and demo mode never persists it.
- Recover from malformed appearance preferences without destroying the file;
  choosing a theme repairs it. Update screenshots and documentation.

### Onboard lighting and recovery

- Remove continuous wireless direct-RGB streaming and reject the old streaming
  API, eliminating its recurring lighting traffic while typing.
- Save Static, Off, and the retained 17 animations onboard through the 2.4 GHz receiver.
  Lighting remains saved after the application closes.
- Offer seven native preset colors for Static and Smooth breathing; migrate old
  arbitrary static colors to the nearest preset. Normalize brightness and speed
  to supported 25-point steps and return normalized demo results.
- Add **Save to keyboard**. Saving local preferences or importing profiles does
  not apply lighting; users explicitly apply changes.
- Disable unverified wired lighting writes while keeping wired input remapping.
- Clear legacy RGB background intent and stop old lighting workers. Do not undo
  or repeatedly reapply lighting on close, quit, login, or a timer.
- Preserve exact-model checks, device-bound backups, fragment acknowledgments,
  and complete read-back verification before reporting a successful save.
- Serialize apply/restore operations; read current settings before each change
  and preserve unrelated keyboard configuration. Skip redundant EEPROM saves.
- Distinguish completed saves from interrupted writes so connection closure
  cannot inadvertently restore an older configuration.
- Roll failed writes back to the immediately preceding settings; retain the
  original backup for explicit **Restore previous lighting** / `rgb --restore`.
- Retain durable recovery information for interrupted saves/restores and recover
  before the next explicit apply. No firmware-write commands were added.
- Fix preset-selector intermediate empty changes accidentally selecting white.

### Remapping and Settings reliability

- Grab only interfaces exposing bound controls for wheel-only remapping, leaving
  a separate typing interface on the normal Linux input path.
- Preserve held-key actions until release when bindings reload, preventing
  unintended typing-key/modifier releases or suppression during wheel edits.
- Recover unmapped held keys and modifiers after input overflow without firing
  mapped shortcuts spuriously. Rebuild interface selection when bindings need it.
- Defer closing Settings while a save or hardware-access operation is active;
  display an explanation and keep theme monitors alive until it finishes.
- Expand regression coverage for appearance, hardware setup, native lighting,
  remapping, recovery, AppImage routing, and login startup.

## Usage notes and validation

The supported keyboard remains the **Redragon K686WBG-RGB-MAX**. Use the 2.4 GHz
receiver to save lighting; wired lighting writes are disabled. Remapping requires
the app to remain running. On GNOME, showing the tray icon requires an
AppIndicator extension; startup and remapping can run without a visible icon.
Polkit and a desktop authentication agent are needed for hardware setup.

Quit with **Quit and stop keyboard services** before replacing an AppImage, then
relaunch it after updating. Keep the image in a stable location. Deleting it
prevents startup at the next login; an already-running instance can continue
until it exits.

The current automated suite passes 150 tests with 19 display-dependent tests
skipped in the headless check. Earlier 0.2.5 validation included all 19 GTK tests,
cross-mount daemon control, and read-only K686 configuration checks on Omarchy.
The release image's update metadata and matching checksums are verified before
publishing. Full GNOME/KDE login cycles and new physical lighting/power-cycle
behavior have not been verified here.
